# 系统架构

本文是“PDF Toolbox 如何工作、为什么这样分层”的唯一权威来源。查找具体文件和修改入口请看[仓库与代码导航](repository-guide.md)；安全约束见[安全规则](safety.md)；阶段计划见[开发路线图](roadmap.md)。

本文会明确区分**当前已经实现的原型**与**下一阶段的目标结构**，避免把计划误写成现状。

## 1. 架构目标

第一版首先是一款可靠的本地只读 PDF 阅读器。架构优先保证：

- 用户文档不离开本机；
- 打开和阅读不会修改输入文件；
- 损坏、加密或超大文件能够安全失败；
- 页面按需渲染，长文档不会一次性占满内存；
- 切换或关闭文档时，旧任务和资源能够可靠释放；
- 未来的合并、拆分、标注和 OCR 可以在只读基础上接入，而不绕过安全边界。

具体产品范围和完成标准由 [product.md](product.md) 定义。

## 2. 当前 P1 原型

当前实现是一条最短的架构验证链路：

```text
用户选择 PDF
    ↓
WebView 文件选择器返回 File 对象
    ↓
File.arrayBuffer() 将整份文件读入内存
    ↓
PDF.js Worker 解析文档
    ↓
取得第一页并渲染到 Canvas
    ↓
界面显示文件名、大小、页数或错误状态
```

当前边界：

- React/TypeScript 承担文件选择、PDF.js 生命周期、第一页渲染和界面状态；
- Rust/Tauri 只创建受限桌面窗口，尚未读取 PDF，也没有文件写入命令；
- PDF.js 是唯一的 PDF 解析与渲染实现；
- 加密文件只显示需要密码，不尝试解密；
- 输入文件没有保存、覆盖或修改路径；
- 每份文件会被完整读入内存，因此当前方案尚不适合超大 PDF。

这套结构证明了 Tauri、WebView2、PDF.js Worker 和 CSP 可以协同运行，但它还不是完整阅读器。

## 3. P2 阅读器目标结构

下一阶段在不增加写入能力的前提下，将原型拆成四个职责区域：

```text
┌──────────────────────────────────────────────────┐
│ React UI                                         │
│ 工具栏、状态、页面列表、滚动、缩放和用户操作     │
├──────────────────────────────────────────────────┤
│ Viewer                                           │
│ 页面占位、可见区域检测、按需渲染和 Canvas 回收   │
├──────────────────────────────────────────────────┤
│ PDF adapter / Document session                   │
│ PDF.js 封装、文档状态、任务取消和错误归类        │
├──────────────────────────────────────────────────┤
│ Tauri + Rust                                     │
│ 受限桌面能力；文件服务是否下沉由大文件实验决定   │
└──────────────────────────────────────────────────┘
```

P2 不引入 qpdf 或 Tesseract。它们分别属于页面写入和 OCR 阶段，过早加入只会扩大依赖与安全面。

## 4. 模块职责

### UI shell

负责窗口布局、工具栏、状态栏和用户操作。UI 只消费结构化状态，不直接管理 PDF.js Worker 或拼接底层错误。

原型阶段只提供英文界面，用户可见文案集中在 `src/i18n/en.ts`；语言策略不参与业务判断。

### DocumentSession

每个打开的 PDF 对应一个会话，负责：

- 文档显示名称、大小和页数；
- PDF.js 加载任务与文档实例；
- 当前会话编号；
- 正在进行的页面渲染任务；
- 加载、就绪、密码、错误和关闭状态；
- 关闭时销毁 Worker、任务、页面引用和缓存。

用户切换文件后，旧会话即使异步返回也不能更新新界面。当前原型已经用操作编号保护第一页加载；P2 会把该规则集中到 DocumentSession。

### Viewer

Viewer 负责展示文档，而不是拥有文档生命周期：

- 为所有页面建立尺寸占位；
- 只渲染当前视口及少量相邻页面；
- 限制并发渲染数量；
- 快速滚动时降低远处页面优先级或取消任务；
- 页面远离视口后释放 Canvas/位图；
- 根据视口计算当前页；
- 应用缩放和适合宽度等显示策略。

页面渲染结果是可丢弃缓存，不是永久状态。

### PDF adapter

隔离 PDF.js 的具体 API，并把库的异常映射为项目自己的错误类别。这样升级 PDF.js、增加测试或添加界面语言时，不需要让组件依赖库的错误字符串。

初始错误模型：

- `password-required`；
- `invalid-or-damaged-pdf`；
- `unsupported-feature`；
- `out-of-memory-risk`；
- `read-failed`；
- `render-failed`；
- `cancelled`；
- `unexpected`。

### Tauri / Rust boundary

当前 Rust 没有读取 PDF。是否将文件访问下沉到 Rust，取决于 P1 的大文件测量结果：

- 若整文件读取的内存与性能可以接受，P2 可继续保持最小 Rust 边界；
- 若不可接受，再设计受控的分段读取或本地协议；
- 无论采用哪种方案，前端都不能把任意字符串作为 Shell 命令交给 Rust；
- 新增文件系统、Shell、网络或外部程序能力前，必须同步审查 Tauri capabilities 和 [safety.md](safety.md)。

## 5. 生命周期与状态原则

```text
empty → loading → ready
           ├──→ password-required
           ├──→ error
           └──→ cancelled
ready → closing → empty
```

必须遵守：

- 文档事实只有一个来源；
- 同一时刻最多只有一个活动文档会话；
- 每项异步结果必须验证自己仍属于当前会话；
- 打开新文件会先取消并销毁旧会话；
- 页面任务失败不应使整个应用退出；
- 长期监听器、Worker、Canvas 和文件句柄必须有明确销毁路径；
- 错误日志不得包含 PDF 正文或不必要的敏感路径。

## 6. 大文件与渲染预算

当前 `File.arrayBuffer()` 至少产生一份完整文件内存副本，是已知限制。进入 P2 前后需要测量：

- 不同大小 PDF 的读取、解析和首屏时间；
- 文件字节、PDF.js 内部结构、Canvas 与位图分别占用多少内存；
- 关闭或切换文件后内存是否回落；
- 高 DPI、缩放和快速滚动时合理的并发数与缓存预算。

在得到测量结果前，不凭猜测引入复杂的 Rust 文件协议。页面按需渲染和缓存回收则是 P2 的必备能力。

## 7. 未来写入边界

只读阅读器稳定后，页面操作采用“操作计划”，而不是每次交互立即改写 PDF：

```text
只读输入 + 页面操作计划
          ↓
       临时输出
          ↓
   结构与可打开性验证
          ↓
 用户明确选择的目标文件
```

qpdf、合并拆分、标注和 OCR 必须遵守 [safety.md](safety.md) 中的写入协议。阅读器模块不得获得隐式覆盖原文件的能力。

## 8. 尚待验证的架构问题

1. 100 MB 级及更大 PDF 使用整文件读取时的峰值内存；
2. 关闭和快速切换文件后 Worker、任务与内存是否释放；
3. 页面尺寸预取与占位布局的成本；
4. 高 DPI、缩放和快速滚动时的并发与缓存预算；
5. 超大文件是否需要 Rust 分段读取；
6. 密码输入功能是否在 P2 实现，以及凭据如何只驻留内存。

实验结果记录在 `docs/validation/`，形成长期技术选择时再建立 ADR。
