# 给 C 使用者的 Rust/Tauri 心智模型

本文是面向熟悉 C 的参与者的学习附录，不定义系统架构或代码布局。项目的实际 Rust 职责见[系统架构](architecture.md)，具体文件入口见[仓库与代码导航](repository-guide.md)。

不需要先学完 Rust 才能参与这个项目。先建立下面这些对应关系即可。

## 1. 熟悉的部分

Rust 仍然是编译型语言：

```text
源代码 → 编译器 → 本机可执行文件
```

- `cargo` 类似构建系统加包管理器；
- `Cargo.toml` 类似项目配置和依赖清单；
- `fn` 是函数；
- `struct` 仍然是结构体；
- `enum` 比 C 的枚举更强，可以携带不同类型的数据；
- `Result<T, E>` 表示成功得到 T，失败得到 E；
- `Option<T>` 表示有值或没有值，避免用空指针表达所有情况。

## 2. 最大区别：所有权

C 里经常需要自己回答：

```text
这块内存是谁申请的？
谁负责释放？
现在这个指针还有效吗？
另一个线程会不会同时修改它？
```

Rust 会在编译期检查大量此类问题。常见结果不是“程序运行后偶尔炸掉”，而是“代码暂时编不过，必须把资源关系说明白”。

这会让开始阶段显得啰嗦，但对处理用户文件的桌面程序很有价值。

## 3. Rust 不能自动保证的一切

Rust 可以减少内存安全错误，但不会自动阻止：

- 写错目标路径；
- 覆盖用户文件；
- 删除不该删除的文件；
- 把密码写入日志；
- 错误调用外部程序；
- 生成语义错误但结构合法的 PDF；
- UI 逻辑错误。

因此 `safety.md` 和测试仍然比语言选择更重要。

## 4. Tauri 中 Rust 的职责

第一版 Rust 代码应当很少，并集中在边界处：

```text
界面请求打开文件
    ↓
Rust 确认这是用户选择的可读文件
    ↓
Rust 返回受控的文档会话信息
    ↓
界面和 PDF.js 显示文档
```

不会为了“全 Rust”而把 React 或 PDF.js 已经擅长的工作重写一遍。

## 5. 错误处理思路

C 中常见返回码：

```c
int open_document(...); // 0 成功，其他值失败
```

Rust 更倾向于：

```text
Result<DocumentSession, OpenDocumentError>
```

调用者必须显式处理成功和失败。错误还能进一步区分无权限、需要密码、文件损坏等情况。

## 6. 这个项目需要先掌握的 Rust 内容

只需按出现顺序学习：

1. 变量、函数和结构体；
2. `Option` 和 `Result`；
3. `match`；
4. 借用 `&T` 与可变借用 `&mut T`；
5. `String`、`Path`、`PathBuf`；
6. 模块和 Cargo；
7. 异步任务与取消；
8. Tauri 命令和序列化。

暂时不需要研究宏、unsafe、复杂生命周期、嵌入式开发或高级泛型。

## 7. 项目约束

- 业务代码默认禁止 `unsafe`；确需使用必须记录理由并单独审查；
- 不使用 `unwrap()` 处理来自用户文件的失败；
- 文件路径使用 `Path`/`PathBuf`，不使用字符串拼接；
- 错误需要保留技术原因，同时映射为用户可理解的类别；
- 新增系统能力时，Tauri 权限只开放最小范围。
